# Payload CMS

Payload 3.91.0 runs **inside this Next.js app** (no separate server), backed by Postgres (Neon, created 2026-10-24). Built the same way as the Giada project. Setup status and the build plan are in [02-architecture.md](02-architecture.md#payload--neon-status-and-plan).

| Piece | File | Notes |
| --- | --- | --- |

## Scripts

| Command | Purpose |
| --- | --- |
| `npm run generate:types` | Regenerates `src/payload-types.ts`. Run after changing any collection or global. |
| `npm run generate:importmap` | Regenerates `src/app/(payload)/admin/importMap.js`. Run after adding admin components, rich-text features or plugins that add admin components (including **enabling the S3 plugin**). |
| `npm run payload` | Payload CLI (`payload run <script>`, migrations, ...). |
| `npm run seed:home` | Puts today's home page (`src/data` and `public/images`) into the CMS. Refuses the `production` branch and a home page that already has content unless `SEED_PRODUCTION=1` / `SEED_OVERWRITE=1` is set. See `scripts/seed-home.ts`. |

Both generate commands only read the config. They do not connect to a database.

## Access rules (Users)

- **admin:** full access.
- **editor:** can edit site content. Cannot create or delete users, cannot read other users, cannot change their own role. The `role` field has its own field-level lock, because otherwise "an editor may update their own record" would let them promote themselves.
- **The very first account is always an admin**, whatever the Role dropdown says (a `beforeChange` hook). Without it the first account would get the default `editor` role and nobody could manage users (Giada hit this). The form still shows "Editor" selected, and the field description says so.
- Anonymous users cannot list users (403). Media is publicly readable.

## Environment

See `.env.example`. Nothing is required to build the site, but the admin and API need a database.

| Variable | Used for |
| --- | --- |
| `PAYLOAD_SECRET` | Signs admin sessions. Required at runtime. Generate a random 64-character hex string. |
| `DATABASE_URL` | Postgres connection string (Neon pooled URL). |
| `DATABASE_URL_UNPOOLED` | Direct (unpooled) Neon URL, for migrations and tooling. Not read by the app yet. |
| `AWS_ACCESS_KEY_ID`, `AWS_SECRET_ACCESS_KEY`, `AWS_ENDPOINT_URL_S3`, `AWS_REGION` | Neon Object Storage. When `AWS_ENDPOINT_URL_S3` and `AWS_ACCESS_KEY_ID` are empty the storage plugin is **off** and uploads go to the local, gitignored `/media` folder. |
| `REVALIDATE_SECRET` | The secret of `POST /api/revalidate` (header `x-revalidate-secret`). Without it every call is refused. Production needs its own. |

Until `DATABASE_URL` points at a real database, `/admin` and `/api/*` return errors. The public pages do not need it yet.

## Neon: set up and verified (2026-10-24)

**What exists.** Neon project "Learning Paths School" (AWS US East 1, Postgres 18), branch `production` (default) with a private bucket `lps-media`. `neon.ts` declares the bucket; `neon deploy` applies it. A long-lived branch `dev` (**no expiry**, decided 2026-10-24 because the project is long; `neon.ts` gives the branch named `dev` no ttl and any other new branch 7 days) is for local work, with its own database and a copy-on-write copy of the bucket. `.env.local` (gitignored) holds the variables of the branch that is checked out (`neon checkout <branch>` switches them); right now it is `dev`.

**How the app uses it.** No code change was needed: `payload.config.ts` already reads `DATABASE_URL` (pooled, node-postgres through `@payloadcms/db-postgres`, the driver the Neon skills recommend on Vercel) and the `AWS_*` variables (path-style S3, `disableLocalStorage`). The bucket name `lps-media` in the config matches the one in `neon.ts` (keep both in step). Use `DATABASE_URL_UNPOOLED` for migrations.

**Proof (2026-10-24).** Production build passes with the Neon variables. Against production: Postgres answers through the pooled and the direct URL; the bucket takes a put, get and list and then a delete, and an anonymous GET is refused (HTTP 403). Through the running app on the `dev` branch (all 15 checks passed): Payload created its 9 tables; the first user was created and became an admin; `/api/users/me` read it back; a 900x600 PNG uploaded through `/api/media` landed in the bucket with its 400x400 thumbnail (checked with a separate S3 client, right type and size, no local `/media` copy); an anonymous visitor loaded it through the app's URL with identical bytes; the row was in Postgres; deleting through Payload removed both files from the bucket. The test data was deleted afterwards. `neon.ts` plan and deploy showed no pending changes.

## Migrations (since 2026-10-28)

Files in `src/migrations` (generated by `npm run payload -- migrate:create <name>`, committed, excluded from Prettier and ESLint because Payload rewrites `index.ts` itself). `payload migrate` applies the ones not yet applied (recorded in the table `payload_migrations`). It must run with `PAYLOAD_MIGRATING=true`, which makes `payload.config.ts` use the direct connection (`DATABASE_URL_UNPOOLED`) and switch off the automatic schema push (otherwise a run outside production would push the schema instead of applying the files). On Vercel `scripts/vercel-build.mjs` does it before every production and preview build (each on its own Neon branch: `production` and `preview`). In development Payload still pushes schema changes to the `dev` branch by itself.

## Known limitations and gotchas

- **Unknown URLs: solved on 2026-10-21.** With two root layouts Next has no single layout to wrap unmatched URLs in, so they showed a plain 404 without header and footer. `src/app/global-not-found.tsx` (experimental, enabled in `next.config.ts`) now renders a branded 404 with its own `<html>`, fonts, header and footer (HTTP 404, `noindex`). The copy is mine; the real design is still to come. A `not-found.tsx` inside `(frontend)` would cover `notFound()` calls from pages, not unmatched URLs.
- **Without a database, `/admin` and `/api/*` answer 500 in production** (they cannot connect); the static public pages are unaffected. See [16-production-readiness.md](16-production-readiness.md).
- **Cache Components is off** (see [architecture](02-architecture.md#payload--neon-status-and-plan)).
- **Dev auto-creates tables, production does not.** Payload's Postgres adapter pushes schema changes automatically only when `NODE_ENV` is not `production`. So running `npm run dev` against a shared database changes that database immediately, and there are **no migration files**. Use a separate Neon branch for local work, and create real migrations before launch.
- **Do not run a second `next dev` in this folder.** Next.js allows one dev server per project. If one is already running, another start fails with "Another next dev server is already running".
- **Do not delete `.next` while a dev server is running.** Builds can run alongside dev (dev uses `.next/dev`), but wiping `.next` removes the dev server's cache.
- **Changing a collection** needs `npm run generate:types`. **Adding an admin component, rich-text feature or enabling the S3 plugin** needs `npm run generate:importmap`.
- **The admin is always dark** (`admin.theme: "dark"`, 2026-10-28, as Giada): no light mode, no theme switch, whatever the visitor's operating system says. Giada also customises the admin logo; not done here.
- `/api/graphql-playground` is the generated default. Consider removing the GraphQL routes if GraphQL is not going to be used.
